## What This App Is

Codematica is a gamified learning app. V1 is a mobile-first Next.js web app plus an Expo Router Android/iOS app that browse, render, search, and practice AI-authored Markdown and structured study content about system design, programming, coding, production engineering, and beginner human languages.

Markdown files are the durable source of truth. Supabase is scaffolded as an optional sync/search backend and is used for optional Auth/progress when public runtime env vars are configured, but the app must run from the local generated content index without requiring Supabase credentials for anonymous browsing.

Future product areas include:

- AI summaries and study assistance for each article
- flashcards for software engineering concepts
- system design blueprints and visual creation mode
- Mermaid authoring and diagram generation from the app
- code snaps and deeper grading/persistence on top of the editable React/TS playground
- Duolingo-style scoring, progress, streaks, and challenge loops
- expanded Japanese language study with sound, larger dictionaries, and richer writing drills
- richer profiles, deeper saved progress/scoring, and eventually native clients

Frontend is split across `apps/web` for Next.js App Router and `apps/mobile` for Expo Router. Shared content/search/practice/progress logic lives in `packages/core`; shared native screens live in `packages/ui`. Content indexing is local-first. Supabase is optional infrastructure for hosted search, Auth/progress, and later AI workflows.

## Mental Model

- Markdown is canonical. The generated index is an artifact, not an authoring surface.
- The app must remain useful without Supabase for anonymous browsing. Cross-device Auth/progress requires Supabase runtime env vars.
- Routing is content-oriented: `/` shows the learning path map, `/browse` browses the index, `/docs/[...slug]` renders articles, `/diagrams/[...slug]` renders external Mermaid diagrams, and `/languages/japanese` opens the Japanese language study hub.
- Content boundaries are schema-validated. Authored Markdown frontmatter is untrusted until it passes `packages/core/src/content/schema.ts`.
- Search currently runs client-side from `packages/core/src/generated/content-index.json`; future Supabase-backed search should preserve the same user-facing behavior unless a feature doc changes the contract.
- Gamification is intentionally light in V1: tracks, difficulty, progress-ready metadata, and learning UI are present before durable scoring/auth.

## Data Protection

- Treat persisted user, progress, and content data as irreplaceable once Supabase-backed features begin.
- Prefer additive and reversible migrations. `DROP`, mass `DELETE`, destructive backfills, or automatic cleanup that can remove user data are high-risk operations and must not be treated as routine refactors.
- Never expose Supabase service role keys to browser code.
- Keep RLS enabled by default before any hosted/public Supabase use.
- If a task appears to require destructive data changes, stop and document the intended deletion, the recovery path, and why a safer additive approach is not sufficient before proceeding.

## Content Source Of Truth

- Canonical knowledge content lives in `content/knowledge/**/**/*.md`.
- Canonical external Mermaid diagrams live in `content/diagrams/**/*.mmd` or `content/diagrams/**/*.mermaid`.
- Canonical human-language character and vocabulary catalogs live in `content/languages/**/*.json`.
- `packages/core/src/generated/content-index.json` is generated by `npm run content:index`.
- Do not hand-edit generated content index output.
- AI-authored knowledge files must remain plain Markdown, not MDX, unless a future feature doc explicitly changes the content execution model.
- All Markdown frontmatter must pass the Zod contract in `packages/core/src/content/schema.ts`.
- Every durable content feature, content model change, or new content workflow must update the relevant feature doc and the closest applicable README.

## Persistence And Backend

- V1 web and native runtimes read the generated local content index from `packages/core`.
- Supabase is optional for anonymous browsing. Do not make local browsing depend on a remote database.
- Treat repo Markdown as canonical even after enabling Supabase sync.
- `scripts/content/sync-supabase.ts` is the optional sync path.
- `supabase/migrations/` contains optional future tables and RPCs for hosted document/diagram search.
- Browser code must use anon-safe Supabase clients only. Never use service role keys outside server-only scripts.
- Server-only scripts may use service role keys through environment variables; never commit secrets.

## Current Realities And Gotchas

- This is a new project, so docs and structure are part of the product foundation, not cleanup work.
- The UI is mobile-first and currently styled as a bright gamified learning app.
- Search is fuzzy-only in the UI. Do not reintroduce an exact/fuzzy toggle without updating the feature doc and tests.
- Mermaid exists in two forms: embedded fenced blocks inside Markdown and external `.mmd` / `.mermaid` files referenced by frontmatter.
- `packages/core/src/generated/content-index.json` may change when parser logic or content changes; regenerate it intentionally with `npm run content:index`.
- Next dev HMR allows `127.0.0.1` through `allowedDevOrigins` in `next.config.ts`.

## Testing Standard

TDD is the default engineering standard for this repo.

1. Start with a failing automated test whenever you add behavior, fix a bug, or refactor logic with non-trivial risk.
2. Make the smallest production change that turns the test green.
3. Refactor with the tests protecting the behavior.

- Choose the lowest layer that can prove the behavior:
  - unit tests for pure transforms, content parsing, frontmatter validation, search ranking, snippet generation, diagram indexing, and schema boundaries
  - integration tests for generated index loading, renderer behavior, route-level content contracts, and Supabase sync boundaries that do not need a full browser
  - E2E tests for user-visible workflows, routing, mobile layout, article reading, diagram rendering, reload behavior, and critical cross-system journeys
- Do not treat E2E as a substitute for missing unit or integration coverage. Browser tests verify the journey; lower-level tests should pin the business logic underneath it.
- Most non-trivial changes should add or update more than one test layer. If a workflow changes in the UI, add the lower-level regression test that explains the logic and the E2E coverage that proves the user path.
- Every bug fix should begin by reproducing the issue with a failing regression test at the narrowest practical layer. If that is genuinely not feasible, add the closest reliable test and explicitly call out the remaining gap.
- A task is not done until the relevant tests are added or updated, the relevant docs are updated, and the relevant test commands have been run locally.

## E2E Testing

E2E coverage is required for important user-facing workflows, but it complements unit and integration coverage rather than replacing it.

### Architecture

| Component | Location | Purpose |
|-----------|----------|---------|
| Playwright config | `apps/web/e2e/playwright.config.ts` | Test runner config, mobile project, and web server |
| Test specs | `apps/web/e2e/specs/*.{smoke,regression}.spec.ts` | Browser-level test files |
| Test results | `test-results/` | Failure screenshots, traces, and videos; ignored by git |
| HTML report | `playwright-report/` | Local report output; ignored by git |
| Content fixtures | `content/knowledge/`, `content/diagrams/` | Real starter content used by smoke tests |

### Test Naming Conventions

- **`*.smoke.spec.ts`** - Critical path tests. Must be fast and reliable.
- **`*.regression.spec.ts`** - Deeper feature tests for edge cases, failures, and feature-specific workflows.
- Tag tests in the test name string: `@smoke`, `@regression`, or `@critical`.

```typescript
test("@regression verifies fuzzy search ranks title matches first", async ({ page }) => {
  // ...
});
```

### Adding A New E2E Test

#### Step 1: Decide smoke or regression

- **Smoke** if the feature is on the critical user path: browsing, search, article reading, diagram rendering, auth once added, or saved progress once added.
- **Regression** for edge cases, feature-specific workflows, error states, and non-critical flows.

#### Step 2: Create the test file

```text
apps/web/e2e/specs/my-feature.regression.spec.ts
```

#### Step 3: Use deterministic content and setup

- Prefer existing starter content when it proves the behavior.
- If a test needs new content, add small deterministic Markdown/diagram fixtures and update `packages/core/src/generated/content-index.json` with `npm run content:index`.
- Do not depend on remote Supabase for V1 E2E unless the feature explicitly requires it.

#### Step 4: Use existing helpers and stable selectors

- Always check existing specs/helpers before writing raw locator logic.
- Use `data-testid` for elements that tests interact with.
- Naming convention: `{feature}-{element}-{qualifier}`.
- Use `page.getByTestId()` or role queries. Never use CSS class selectors.

#### Step 5: Use `test.step()` for complex flows

Break multi-step tests into named steps when it improves failure readability:

```typescript
test("@regression reads an article and opens its diagram", async ({ page }) => {
  await test.step("open the browser", async () => {
    await page.goto("/");
    await expect(page.getByTestId("knowledge-browser")).toBeVisible();
  });

  await test.step("open a document", async () => {
    await page.getByRole("link", { name: /Cache Invalidation/ }).first().click();
    await expect(page.getByTestId("document-page")).toBeVisible();
  });
});
```

### Modifying Existing Tests When Features Change

#### If a `data-testid` changed

1. Update the selector in the test.
2. Search all test files for the old testid: `rg "old-testid" apps/web/e2e/ apps/web/src/`.
3. Update helpers or page objects if the testid is used there.

#### If a UI flow changed

1. Read the entire test file to understand flow dependencies.
2. Tests may use `test.step()`; each step can depend on state from previous steps.
3. Run the modified test locally before calling the task complete:

```bash
npx playwright test --config=apps/web/e2e/playwright.config.ts apps/web/e2e/specs/my-test.regression.spec.ts
```

#### If content, generated index, or schema changed

1. Run `npm run content:index`.
2. Update parser/search/index tests that reference the changed contract.
3. Run `npm run content:check`.
4. If Supabase migrations changed, update any sync tests/helpers and document the migration behavior.

### Running And Debugging Tests

```bash
# Full smoke suite
npm run e2e:smoke

# Specific test file
npx playwright test --config=apps/web/e2e/playwright.config.ts apps/web/e2e/specs/knowledge-browser.smoke.spec.ts

# Headed browser for visual debugging
npx playwright test --config=apps/web/e2e/playwright.config.ts --headed apps/web/e2e/specs/knowledge-browser.smoke.spec.ts

# Playwright UI mode
npx playwright test --config=apps/web/e2e/playwright.config.ts --ui
```

### Key Rules

1. Never use `page.waitForTimeout()`; use visible UI, route state, or Playwright auto-waiting.
2. Never use CSS class selectors; use `data-testid` or role queries.
3. Keep smoke tests fast. If a test takes more than 60 seconds locally, it should probably be regression.
4. Start below the browser when possible; add unit/integration coverage first, then E2E for the user workflow.
5. Every user-visible regression needs an automated test that would have caught the issue before it shipped.

## Unit And Integration Tests

### Vitest

- Config: `vitest.config.ts`
- Test files: `apps/web/src/**/*.{test,spec}.{ts,tsx}`, `packages/core/src/**/*.{test,spec}.ts`, `packages/ui/src/**/*.{test,spec}.{ts,tsx}`, `scripts/**/*.{test,spec}.ts`
- Run: `npm test` for the full Vitest suite, `npm run test:watch` for watch mode, and `npx vitest run path/to/file.test.ts` for a targeted TDD loop.

### What To Test Where

| Layer | Tool | What To Test |
|-------|------|--------------|
| Unit | Vitest | Pure logic: frontmatter schemas, Markdown parsing, heading extraction, content indexing, search ranking, snippets |
| Integration | Vitest | Generated index loading, renderer behavior, optional Supabase sync boundaries with mocked clients |
| E2E Smoke | Playwright | Critical user paths: browse, search, open article, render Mermaid diagram |
| E2E Regression | Playwright | Feature-specific workflows, edge cases, error states, mobile layout regressions |

Rule of thumb: if you can test it without a browser, do it in Vitest first. Use unit tests for isolated logic, integration tests for multi-module behavior, and reserve E2E for workflows that truly need the browser.

### Coverage Expectations

1. New pure logic or branching behavior should come with unit tests.
2. Changes to content parsing, indexing, search, rendering, Supabase sync, or migrations should come with integration coverage when unit coverage alone cannot prove the contract.
3. Changes to user-visible workflows, routing, mobile layout, diagram rendering, reload behavior, or recovery UX should come with E2E coverage.
4. Changes to migrations, generated content contracts, or fixture-sensitive behavior must update relevant tests and docs.
5. Do not remove or weaken tests just to get green builds unless the product behavior itself is intentionally changing and the test is being rewritten to match the new contract.

## Code Conventions

### React Components

- Reuse existing components before creating new ones. Start every UI task by checking `apps/web/src/components/` and nearby route usage for a component or pattern to extend.
- Prefer adding a small prop, slot, or composition path to an existing component over creating another bespoke component for the same behavior. Less code is good. Reusing is good. Abstracting repeated UI and logic is good.
- Create a new component only when no existing component can reasonably own the behavior, state, styling, or accessibility contract. If you create one, add it to the reusable component inventory in this file and update the relevant docs.
- Use `data-testid` on any element that E2E tests interact with.
- Naming: `{feature}-{element}-{qualifier}`.
- Keep components mobile-first. Verify small viewports for major UI changes.
- Use lucide icons inside buttons and tool controls when an icon exists.
- Treat WCAG AA contrast as a baseline for new UI: normal text and icons must be at least 4.5:1 against their background, large/bold text at least 3:1, and non-text interactive states such as focus rings, borders, and icon-only controls at least 3:1. Verify button/link foreground classes are not overridden by global CSS.
- Avoid nested cards. Cards are for repeated items, modals, and genuinely framed tools.
